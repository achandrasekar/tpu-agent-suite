# TPU v7x Memory and Buffer Sizing

## VMEM Limits and Allocation Scopes

Vector Memory (VMEM) serves as local scratchpad storage dedicated exclusively to the TensorCore (TC)[^xla-scoped-vmem][^openxla-sparsecore]. The XLA compiler divides VMEM allocations into instruction-scoped allocations (temporary buffers for single HLO instructions, such as register spills and double-buffered operand spans) and program-scoped allocations (intermediate buffers and compiler temporaries spanning multiple HLOs)[^xla-scoped-vmem].

Usable scoped VMEM is strictly managed at compile time to avoid Scoped VMEM Out-of-Memory (E1001) errors[^xla-scoped-vmem]. This scoped limit represents reserved compiler headroom rather than total physical SRAM capacity[^xla-scoped-vmem]. Scoped thresholds can be configured globally using `--xla_tpu_scoped_vmem_limit_kib` or overridden per custom kernel using `vmem_limit_bytes`[^xla-scoped-vmem].

## Tile Sizing and Padding

XLA structures memory on TPU vector registers using major-to-minor multidimensional tiled layouts[^openxla-tiled-layout]. The standard layout utilizes $(8, 128)$ tiles matching native 32-bit vector registers, while 16-bit BF16 datatypes apply repeated tiling: $(8, 128)(2, 1)$[^openxla-tiled-layout]. This packs two 16-bit elements from adjacent rows into one 32-bit element to maximize cross-minor dimension throughput[^openxla-tiled-layout].

Whenever an array dimension is not evenly divisible by tile bounds, the array is padded to $\lceil d_i / t_i \rceil \cdot t_i$[^openxla-tiled-layout].

**Resident Tile Calculation (Derived):**
* Target format: BF16 $(8, 128)(2, 1)$ layout[^openxla-tiled-layout].
* Tile element footprint: $8 \times 128 = 1024$ logical elements[^openxla-tiled-layout].
* Data size: At 2 bytes per BF16 element, a single resident tile consumes $1024 \times 2 = 2048$ bytes (derived: $2048 \div 1024 = 2\text{ KiB}$)[^openxla-tiled-layout].

## SparseCore

SparseCore is a specialized tiled processor featuring multiple compute tiles, centralized sequencers, and on-chip scratchpad memory (SPMEM) alongside High Bandwidth Memory (HBM)[^openxla-sparsecore].

The supplied sources do not provide SparseCore hardware specifications for TPU v7x (such as SparseCores per chip, tiles per core, SIMD width, or HBM capacity)[^openxla-sparsecore]. Generic SparseCore memory allocations rely on static compile-time sizing within SPMEM based on parameters such as `max_ids_per_partition` and `max_unique_ids_per_partition`[^openxla-sparsecore]. When operations exceed SPMEM capacity, temporary intermediate buffers spill onto the HBM stack[^openxla-sparsecore].

## Memory Viewer

The XProf Memory Viewer provides a static inspection of peak memory allocations generated by the XLA compiler across program order (HLO sequence)[^xprof-memory-viewer]. Because the tool reflects static schedules rather than dynamic execution over wall-clock time, it cannot track dynamic multi-module co-residence[^xprof-memory-viewer]. It exposes memory allocations across accelerator spaces (including VMEM, SMEM, CMEM, and HBM), highlighting memory overheads introduced by padding tensors to hardware tile boundaries[^xprof-memory-viewer]. Peak usage charts break down buffers by allocation size, program order, and padding overhead[^xprof-memory-viewer].

## Memory Profile

In contrast to the static Memory Viewer, the XProf Memory Profile tool monitors dynamic HBM usage over runtime intervals[^xprof-memory-viewer][^xprof-memory-profile]. It visualizes heap, stack, and unallocated memory across time alongside memory fragmentation percentages[^xprof-memory-profile]. TPU memory profiles frequently present flat allocation graphs due to large upfront compile-time allocations executed by XLA's runtime allocator rather than dynamic runtime churn[^xprof-memory-profile]. The tool enables host and memory selector filtering to pinpoint peak utilization and framework-level operator memory footprints[^xprof-memory-profile].

## DMA Utilization

Visualizing data motion across a TPU chip's two Tensor Nodes is supported in the Utilization Viewer[^xprof-utilization-viewer]. DMA path utilization measures the fraction of bandwidth (bytes per cycle) consumed over a profiling period, derived via hardware `NF_CTRL` counters[^xprof-utilization-viewer]. The tool monitors 14 distinct DMA interconnect paths connecting seven node domains: HIB (host memory transfers), HBM, Instruction Memory (IMem), Scalar Memory (SMem), Vector Memory (VMem), BMem, and the Inter-Chip Interconnect (ICI)[^xprof-utilization-viewer].

## Trace-Buffer Overflow

Fine-grained custom kernel analysis requires `xprof >= 2.24.0` and its Low-Level Optimizer (LLO) tools[^xprof-custom-call]. Activating runtime bundle tracing via `--xla_xprof_enable_custom_call_tracing=true` instruments instruction bundles, which inflates trace footprints[^xprof-custom-call]. On TPU v7x ($2\times 2\times 1$), an evaluated FlashAttention trace expands $12.3\times$ from 115 MB to 1.42 GB[^xprof-custom-call].

This volumetric expansion can overflow hardware trace buffers, dropping outer HLO lifecycle markers[^xprof-custom-call]. Overflows are mitigated by throttling `xla_tpu_bundle_instrumentation_options`[^xprof-custom-call]:
* `trace_best_effort_frequency`: Interval for inserting traces into existing bundles (default: 10)[^xprof-custom-call].
* `trace_guaranteed_frequency`: Maximum bundle interval before forcing a dedicated trace bundle (default: 10)[^xprof-custom-call].

Hardware performance counter sampling (`tpu_enable_periodic_counter_sampling`) is supported on Ironwood TPU7x+[^xprof-custom-call].

The supplied GitHub documents are the scope of the gaps below. For generation specifications such as HBM capacity, see the [hardware overview](overview.md).

LLO timestamps between trace points are interpolated from hardware-cost estimates, rather than individually measured instruction timestamps.[^xprof-custom-call]
